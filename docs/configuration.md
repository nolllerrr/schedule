# Настройки

Настройки читает [`Settings.from_env`](../src/schedule_bot/config.py). При локальном запуске переменные окружения имеют приоритет над `.env` из текущего каталога. Compose передаёт значения через `env_file: .env`.

В `.env` используются строки `КЛЮЧ=значение`, пустые строки и комментарии, начинающиеся с `#`. Встроенный загрузчик снимает внешние кавычки; подстановка `${VAR}`, префикс `export` и многострочные значения не поддерживаются.

## Telegram и доступ

| Переменная | По умолчанию | Назначение и ограничения |
| --- | --- | --- |
| `BOT_TOKEN` | Пусто | Токен BotFather; обязателен для `run` и `doctor` |
| `ADMIN_TELEGRAM_IDS` | Пусто | Telegram ID администраторов через запятую; пустое значение отключает административный доступ и адресную отправку оповещений |
| `TELEGRAM_PROXY_URL` | Пусто | HTTP- или SOCKS-прокси для Telegram; пусто — прямое подключение |
| `TELEGRAM_FORCE_IPV4` | `true` | Принудительный IPv4 для Telegram; истина: `1/true/yes/on`, ложь: `0/false/no/off`, регистр не важен |
| `TELEGRAM_REQUEST_RETRIES` | `5` | Общее число попыток одного запроса при `TelegramNetworkError`; минимум 1, меньшие целые приводятся к 1 |
| `TELEGRAM_RETRY_SECONDS` | `15` | Пауза перед повторным запуском polling после сетевой ошибки; минимум 5 секунд, меньшие целые приводятся к 5 |
| `TELEGRAM_MAX_CONCURRENT_UPDATES` | `32` | Число одновременно обрабатываемых Telegram updates; целое 1–256 |
| `FSM_STATE_TTL_SECONDS` | `1800` | Время неактивности незавершённого выбора преподавателя; целое 1–86400 секунд |
| `FSM_MAX_RECORDS` | `5000` | Число активных записей незавершённых диалогов; целое 1–100000; при заполнении вытесняется самая давно неактивная |

Сетевые повторы запросов Telegram и повторный запуск polling — разные механизмы. Повторные доставки очереди описаны в [обслуживании](operations.md#доставка-уведомлений).

## Источник и расписание

| Переменная | По умолчанию | Назначение и ограничения |
| --- | --- | --- |
| `SCHEDULE_PAGE_URL` | `https://ptgh.onego.ru/9006/` | Страница расписания с поддерживаемой структурой HTML; корпус 1 выбран в коде |
| `SCHEDULE_PROXY_URL` | Пусто | HTTP-прокси с HTTPS CONNECT для страницы и Excel, например `http://USER:PASSWORD@HOST:PORT` |
| `SCHEDULE_HTTP_MAX_ATTEMPTS` | `4` | Общее число попыток одного HTTP-запроса, включая первую; целое 1–10 |
| `SCHEDULE_HTTP_RETRY_MAX_DELAY` | `15` | Верхняя граница одной паузы между HTTP-попытками; конечное число 0–60 секунд |
| `SCHEDULE_OUTAGE_FAILURE_THRESHOLD` | `3` | Число неудачных автоматических проверок подряд до предупреждения; целое 1–100 |
| `PUBLICATION_LOOKBACK_DAYS` | `14` | Глубина проверки опубликованных файлов назад от текущей даты; целое 0–366 |
| `PUBLICATION_LOOKAHEAD_DAYS` | `60` | Горизонт проверки вперёд; целое 1–366 |
| `PUBLICATION_MAX_FILES` | `32` | Предельное число файлов одной проверки; целое 1–128; превышение останавливает проверку |
| `SCHEDULE_STALE_AFTER_MINUTES` | `120` | Через сколько минут после успешного принятия данных показывать возможную устарелость; целое 1–10080 |
| `CHECK_INTERVAL_MINUTES` | `30` | Интервал автоматических проверок источника; минимум 1 минута, меньшие целые приводятся к 1 |
| `SCHEDULE_SIGNAL_BOT_USERNAME` | Пусто | Бот, чьи сообщения запускают внеочередную проверку сайта, например `@ptghautoraspisaniebot`; пусто — обработчик выключен |
| `SCHEDULE_SIGNAL_CHAT_ID` | `0` | ID общего чата для сигналов; при включённом обработчике обязателен отрицательный Telegram ID группы |
| `SCHEDULE_SIGNAL_COOLDOWN_SECONDS` | `60` | Минимальная пауза между внеочередными проверками; целое 30–3600 секунд; серия сообщений объединяется в одну ожидающую проверку |
| `PIN_SYNC_INTERVAL_MINUTES` | `5` | Интервал проверки закреплений; минимум 1 минута, меньшие целые приводятся к 1 |
| `TIMEZONE` | `Europe/Moscow` | Часовой пояс IANA для учебных дат, закреплений и задач планировщика |

Прокси источника и Telegram независимы. Загрузчик источника отключает `trust_env`: общие `HTTP_PROXY`/`HTTPS_PROXY` не заменяют `SCHEDULE_PROXY_URL`. На SSH эти настройки не влияют.

Сигналы принимаются только от указанного бота в выбранном чате, если он активен и настроен через `/setup`. Учитываются новые сообщения и правки текста, подписи или документа; повторная доставка того же сообщения игнорируется. Бот не отвечает отправителю сигнала: он запускает обычную загрузку с сайта с проверкой изменений, очередью уведомлений и обновлением закрепления. Проверка по таймеру продолжает работать. Если другая проверка уже выполняется, сигнал ожидает освобождения общей блокировки.

Для получения обычных сообщений другого бота включите **Bot-to-Bot Communication Mode** у нашего бота в BotFather и назначьте его администратором чата либо отключите **Group Privacy**. Переключатель сам по себе не включает обработчик: также задайте `SCHEDULE_SIGNAL_BOT_USERNAME` и `SCHEDULE_SIGNAL_CHAT_ID` и примените окружение.

## Реакции Grok

Образ Docker включает закреплённый Grok CLI и постоянный volume авторизации. Первичный вход и порядок включения на сервере — в [инструкции для продакшена](grok-production.md).

| Переменная | По умолчанию | Назначение и ограничения |
| --- | --- | --- |
| `GROK_REACTIONS_ENABLED` | `false` | Включает фоновые комментарии к новым публикациям и изменениям расписания |
| `GROK_CLI_PATH` | `grok` | Исполняемый файл Grok CLI; должен быть доступен в окружении процесса бота |
| `GROK_TIMEOUT_SECONDS` | `30` | Конечный положительный таймаут одной генерации в секундах |
| `GROK_REACTION_CHAT_TYPES` | `group,supergroup` | Типы чатов для реакций, через запятую |
| `GROK_REACTION_CHAT_IDS` | Пусто | Разрешённые ID групповых чатов через запятую; пустой список отключает все комментарии и вызовы Grok для рассылки |
| `GROK_REACTION_CONFIG` | Пусто | Дополнительный JSON с переопределениями настроек генератора |

Генератор находится в [`schedule_grok`](../src/schedule_grok/README.md), его исходный промпт и ограничения — в [`config.json`](../src/schedule_grok/config.json). Этот JSON включается в Python-пакет. Реакции подключены к `/update`, проверкам по таймеру и сигналам другого бота; по умолчанию они выключены. Для реальной генерации нужны установленный Grok CLI и настроенный доступ к нему. Код подключения перенесён с сервера; комментарии отправляются отдельно от очереди основных уведомлений и могут появиться раньше доставки самого расписания.

Для комментариев в одном чате задайте одновременно `GROK_REACTIONS_ENABLED=true` и `GROK_REACTION_CHAT_IDS=<отрицательный ID этого чата>`. Фильтрация выполняется до генерации: уведомления остальных чатов не расходуют лимит Grok. Обычная рассылка расписания работает независимо от этого списка. Локальный и серверный экземпляры читают каждый свой `.env`; список разрешённых чатов нужно отдельно применить на каждом экземпляре.

## Хранение, копии и статистика

| Переменная | По умолчанию | Назначение и ограничения |
| --- | --- | --- |
| `DATABASE_PATH` | `data/schedule.db` | Файл SQLite; относительно текущего рабочего каталога |
| `DOWNLOADS_PATH` | `data/downloads` | Загруженные Excel-файлы |
| `BACKUPS_PATH` | `data/backups` | Резервные копии базы |
| `BACKUP_RETENTION_COUNT` | `14` | Число обычных копий `schedule-*.db`; минимум 1, меньшие целые приводятся к 1 |
| `LOG_RETENTION_DAYS` | `90` | Число сохраняемых дневных архивов файлового журнала; минимум 1, меньшие целые приводятся к 1 |
| `ANALYTICS_SALT` | Пусто | Явный постоянный секрет HMAC; если пусто, `run` использует отдельный файл ключа рядом с базой |
| `ANALYTICS_PREVIOUS_SALTS` | `[]` | JSON-массив до 16 прежних непустых секретов; нужен для удаления статистики после ротации |
| `ANALYTICS_RETENTION_DAYS` | `90` | Срок хранения подробных событий; минимум 1 день, меньшие целые приводятся к 1 |
| `OUTBOX_RETENTION_DAYS` | `90` | Хранение завершённых технических серий доставки; целое 7–3650 дней |
| `DOWNLOADS_RETENTION_DAYS` | `90` | Возраст незащищённых скачанных XLSX для очистки; целое 7–3650 дней |

Файловый журнал бота находится в `logs/bot.log` рядом с файлом базы: при стандартных путях это `data/logs/bot.log`. Его ротация использует UTC независимо от `TIMEZONE`. Копии перед миграцией хранятся отдельно от обычной ротации.

Если `ANALYTICS_SALT` не задан, первый запуск `run` сохраняет прежний ключ, равный `BOT_TOKEN`, в файл `<DATABASE_PATH>.analytics-salt`, например `data/schedule.db.analytics-salt`. Дальше ключ читается из этого файла и не меняется при замене токена. Без токена создаётся случайный ключ. Чтение настроек и диагностические CLI-команды файл не создают. Повреждённый файл ключа останавливает запуск, чтобы не менять идентификаторы незаметно.

Сохраняйте файл ключа вместе с базой; SQLite backup не включает его. Явный `ANALYTICS_SALT` имеет приоритет. При намеренной ротации укажите новый секрет в `ANALYTICS_SALT`, а прежние — в `ANALYTICS_PREVIOUS_SALTS`, например `["прежний-секрет"]`. `/delete_me` использует текущий и все настроенные прежние ключи. Храните их до истечения срока старых событий. Если прежний секрет потерян, связать старые HMAC-события с пользователем уже нельзя; они удалятся по обычному сроку хранения. Секреты не должны попадать в Git и журналы.

## Применение изменений

Рабочие секреты сохраняйте в `.env`; в `.env.example` остаются только пустые поля и безопасные значения по умолчанию.

После изменения `.env` в Docker выполните:

```sh
docker compose up -d --no-build
```

Это пересоздаёт сервис при изменившейся конфигурации окружения. Обычный `docker compose restart` новое окружение не перечитывает. При локальном запуске перезапустите процесс; уже заданные в оболочке значения по-прежнему имеют приоритет над `.env`.
