# Устройство и разработка

Приложение состоит из загрузчика источника, парсера, слоя SQLite, Telegram-интерфейса и фоновых обработчиков. Оно запускается через [`cli.py`](../src/schedule_bot/cli.py). Docker использует Python 3.12; пакет требует Python 3.12+ и aiogram 3.31+ в пределах версии 3. Остальные зависимости заданы в [`pyproject.toml`](../pyproject.toml).

## Запуск и фоновые задачи

`run` подготавливает резервную копию перед нужной миграцией, инициализирует репозиторий, создаёт Telegram-сессию, аналитику, уведомитель, мониторинг и сервис обновления. Затем запускает планировщик, worker доставки, начальную проверку источника и синхронизацию закреплений. Telegram updates поступают через long polling; отдельный HTTP-сервер приложения не нужен.

| Задача | Когда выполняется |
| --- | --- |
| Проверка источника | Сразу при запуске и далее по `CHECK_INTERVAL_MINUTES` |
| Синхронизация закреплений | Сразу при запуске, после обновления и по `PIN_SYNC_INTERVAL_MINUTES` |
| Обычная копия SQLite | В 03:30 по `TIMEZONE` |
| Очистка подробной статистики | В 04:00 по `TIMEZONE` |
| Очистка завершённых очередей и незащищённых XLSX | В 04:30 по `TIMEZONE`, ограниченным пакетом |
| Heartbeat готовности | Каждые 5 секунд в `runtime-health.json` рядом с базой |
| Доставка очередей | Постоянный worker, пробуждение после импорта/оповещения и ожидание до 5 секунд в простое |

Ручные и автоматические обновления в одном процессе используют общую блокировку. Занятая проверка по таймеру не ставит ещё одну за собой: очередной запуск пропускается. Дополнительный сигнал от настроенного бота ожидает освобождения блокировки; серия сообщений объединяется в одну ожидающую проверку с паузой после предыдущей. Обработчик сигналов запускается только при заданных отправителе и ID чата и останавливается вместе с polling. Закрепления используют свою общую блокировку и блокировки отдельных чатов. Доставка и удаление профиля синхронизируются по адресату.

`ExpiringMemoryStorage` хранит только активный выбор преподавателя: записи истекают по неактивности, очищаются таймером и вытесняются при заполнении ёмкости. Профили сохраняются в SQLite и не зависят от этого временного состояния. Параллельность обработки Telegram updates ограничивается настройкой.

## Модель занятия

Точные поля `Lesson`:

| Поле | Тип и смысл |
| --- | --- |
| `lesson_date` | `date`, дата занятия; `to_dict()` переводит её в ISO-строку |
| `group_name` | `str`, нормализованное название группы |
| `position` | `int`, порядковая позиция блока внутри дня |
| `lesson_label` | `str`, исходная нормализованная метка, например `2 пара` или `кл.час` |
| `lesson_number` | `int` или `None`, числовой номер пары |
| `start_time`, `end_time` | Строки времени или `None` |
| `subject` | `str`, дисциплина |
| `teacher`, `room`, `subgroup` | Строки или `None` |
| `raw_data` | `dict[str, str]`, координаты и нормализованные значения исходных ячеек |
| `segments` | `tuple[LessonSegment, ...]`, связанные части пары: предмет, преподаватель, аудитория и подгруппа |

Сводные поля `subject` / `teacher` / `room` сохраняют совместимость со старой моделью. Связи параллельных подгрупп хранятся в `segments`; преподавательская выдача проецирует только его части. Миграция оставляет старым строкам `segments=[]`, не угадывая утраченные связи.

Имя файла относится к `ParsedSchedule.source_filename` и записи импорта, а не к отдельному полю `Lesson`. `ParsedSchedule` также содержит диапазон, распознанные даты, охват групп, предупреждения, ошибки и явно пустые дни. `ImportResult` для известного SHA может содержать только сохранённые метаданные без повторного `ParsedSchedule`.

## База данных

SQLite использует WAL, внешние ключи и `busy_timeout` 5 секунд. Текущая версия схемы — 9. Миграции выполняются последовательно и транзакционно; программа отказывается работать с более новой схемой, чем поддерживает.

| Таблицы | Что хранится |
| --- | --- |
| `imports`, `schedule_dates`, `lessons` | Неизменяемые снимки источников и эффективных импортов; `is_current` отмечает активные занятия; `segments_json` хранит части пары, `empty_dates_json` — явно пустые дни |
| `source_publications`, `active_schedule_dates` | URL и версии источников; победитель и effective import отдельно для каждой активной даты |
| `sync_status` | Время попытки, успешной загрузки, принятия данных и последняя ошибка обновления |
| `user_profiles`, `chat_profiles` | Личные и групповые настройки; групповые поля также содержат подтверждённое закрепление, кандидата и срок повтора |
| `notification_outbox` | Подготовленные части пользовательских и групповых уведомлений |
| `quarantined_imports` | SHA, причины и снимки отклонённых результатов |
| `usage_events` | Псевдонимизированные события использования |
| `schedule_source_health`, `schedule_outage_incidents` | Состояние источника и история инцидентов |
| `admin_notification_outbox` | Предупреждения, восстановления и критические ошибки для администраторов |
| `delivery_attempts` | Начало и исход попытки, известный Telegram message ID и отметка операторской проверки |

Новый файл обновляет текущие занятия только на принятых датах своей публикации. Данные других дат сохраняются. Поэтому «текущая версия расписания» может состоять из нескольких разных импортов. Старые редакции остаются в базе; пользовательский выбор даты читает актуальные строки этой даты.

## Транзакция импорта

1. Сервис выбирает все публикации в настроенном окне. Сетевая часть ограничена общим дедлайном 300 секунд. Сохранённый SHA вместе с диапазоном имени позволяет пропустить повторный разбор.
2. Новый файл разбирается с размерными бюджетами. Стандартный сетевой парсер и CLI `parse` запускают отдельный процесс с дедлайном 60 секунд; `import-file` остаётся синхронным.
3. Под `BEGIN IMMEDIATE` сохраняются снимки источников и выбирается победитель каждой даты. Более узкий диапазон выигрывает; различающиеся публикации одинакового приоритета блокируются. Дата без кандидатов сохраняет прежнее активное расписание.
4. Проверяются структура источников и аномалии относительно их прежних версий, затем — собранное расписание относительно текущих занятий и охвата. Это защищает и случай возвращения известного проигрывающего снимка. Карантин не заменяет активные данные.
5. Сопоставление сначала сохраняет неизменные пары, затем находит прежнее содержимое в других слотах, после чего описывает замены, добавления и удаления. Чистый геометрический сдвиг при прежних метке и времени не создаёт изменение, реальный перенос остаётся видимым.
6. Записываются отдельный effective import, активные занятия и владельцы дат. Для включённых подписок готовится неизменяемый текст и вставляется outbox.
7. Один commit фиксирует активацию и очередь. Ошибка подготовки текста или записи очереди откатывает обе операции. Сохранённые source snapshots и события активации не подменяют друг друга.

Повторная проверка неизменного состава победителей не создаёт новую рассылку. `new_dates` относится к ранее активированным датам, а не истории конкретного подписчика. Правила сообщений описаны в [пользовании ботом](usage.md#уведомления).

Преподаватель ищется по регистронезависимому фрагменту имени. Выдача и уведомления фильтруют связанные части пары; изменение другой подгруппы не приписывается выбранному преподавателю.

## Ресурсы и восстановление фоновых операций

Вызовы SQLite из async UI и закреплений выполняются в потоках с общим лимитом восьми операций на базу и event loop. Отмена ждёт завершения уже запущенной операции до освобождения внешней блокировки. Импорт, доставка, статистика и копирование также выносят синхронную работу из event loop.

Один проход worker имеет бюджет 100 записей обеих очередей; неудачи тоже расходуют бюджет. Подтверждение доставки защищено от штатной отмены задачи, а ошибка аналитики не возвращает отправленную часть в очередь. Блокировки адресатов и чатов освобождаются, когда ими больше никто не пользуется; истёкшие ограничения частоты отправки очищаются. Статистика агрегируется в SQLite, задания рассылки вставляются из генератора.

Для закрепления сохраняются дата, хеш, ID подтверждённого сообщения и ID кандидата. Кандидат переиспользуется после сбоя и перезапуска, задержка повторов растёт от пяти минут до часа. Неизменившееся закрепление не требует запросов Telegram. Изменение предупреждения о давности входит в стабильный хеш сообщения, без обновления времени в каждом цикле. Сегодняшний день считается завершённым только при корректном времени окончания всех занятий; поиск будущего дня ограничен выборкой опубликованных дат и не подставляет архивные даты.

Поведение закреплений описано в [инструкции](usage.md#закреплённое-расписание), правила повторной доставки и граница гарантий — в [обслуживании](operations.md#доставка-уведомлений).

## Проверка изменений

В Windows установите зависимости разработки и запустите тесты:

```powershell
.\.venv\Scripts\python.exe -m pip install --require-hashes -r build-requirements.lock -r dev-requirements.lock
.\.venv\Scripts\python.exe -m pip install --no-deps --no-build-isolation -e .
.\.venv\Scripts\python.exe -m ruff check --select F src tests scripts
.\.venv\Scripts\python.exe -m pytest --basetemp=.pytest-tmp-run
```

В Linux используйте `.venv/bin/python` с теми же аргументами. Синтетические книги создаются в `tests/conftest.py`; реальный исходный Excel в репозитории отсутствует. Обычные тесты используют временные базы и подмены сетевых клиентов, поэтому не требуют рабочего токена и не отправляют сообщения людям.

[Workflow checks](../.github/workflows/checks.yml) запускает проверку актуальности lock-экспортов, Ruff F, pytest, сборку образа и offline smoke check инициализации SQLite. Runtime/build/dev зависимости закреплены lock-файлами с хешами, а базовый Docker-образ — digest. Обновление зависимостей: `uv lock --upgrade`, затем `python scripts/update_locks.py` и проверки. Наличие workflow не включает защиту ветки: required check `checks / test-and-build` настраивается отдельно в GitHub. Результат удалённого CI проверяется для конкретного коммита.

Нагрузочная рассылка включается отдельно:

```powershell
$env:RUN_STRESS_TEST = "1"
$env:STRESS_USERS = "1000"
$env:STRESS_SEND_DELAY_MS = "0"
.\.venv\Scripts\python.exe -m pytest tests/test_stress_notifications.py -s --basetemp=.pytest-tmp-stress
Remove-Item Env:RUN_STRESS_TEST
Remove-Item Env:STRESS_USERS
Remove-Item Env:STRESS_SEND_DELAY_MS
```

Она создаёт временную базу и имитирует Telegram. `STRESS_SEND_DELAY_MS` добавляет задержку одной имитируемой отправки. Интервалы настоящего ограничителя рассылки в тесте отключены: результат характеризует локальную очередь и worker, а не реальную скорость Telegram. Время `enqueue_s` в текущем тесте измеряет `notify_import` после commit; подготовка очереди происходит раньше внутри `import_schedule` и этой величиной не измеряется.
