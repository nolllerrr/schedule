# Защита комментариев Grok — 20 октября 2026

Проверена выдержка аудита от 19 октября для ревизии `354a813`. Пользователь выбрал **best-effort**: пропущенный при сбое комментарий допустим. Основное расписание продолжает использовать свой долговременный outbox.

| Замечание | Принятое поведение |
| --- | --- |
| AUD-03 · Надёжность | Одна попытка комментария в рамках процесса; задания, готовый текст и повтор после перезапуска не сохраняются. Отдельная надёжная очередь не требуется по выбранной гарантии |
| AUD-04 · Настройки чата | Проверяются active, notifications, тип чата, allowlist и исходная группа. Во время генерации разрешение проверяется повторно; перед send проверка выполняется под общей блокировкой с изменением настроек чата |
| AUD-05 · Порядок | Генерация начинается после durable `sent` **всех частей** соответствующей серии расписания. Pending/backoff ожидаются в пределах TTL; failed, устаревшие или отменённые серии пропускаются |
| AUD-06 · Выборка | SQL выбирает только групповые доставки разрешённых чатов с JOIN текущего профиля. Allowlist и результат ограничены 64 чатами; private-адресаты не извлекаются в Python |
| AUD-07 · Процессы | Один runtime worker, не более 8 ожидающих заданий, TTL 300 секунд. При переполнении удаляется самое старое ожидающее задание. Генератор дополнительно ограничивает CLI одним процессом на event loop |
| AUD-08 · Вывод CLI | stdout ограничен 128 КиБ, stderr — 64 КиБ, оба потока читаются одновременно. Превышение, timeout и отмена завершают процесс; оставшийся вывод сбрасывается без накопления в памяти |
| AUD-15 · Сборка | Доступен target `core`, который не скачивает Grok. Target `with-grok` остаётся стандартным для существующего продакшена; CI проверяет оба варианта |
| AUD-18 · Логи | Сохраняются import/delivery ID, статус, длина и короткий SHA-256. Текст реакции, stderr и содержимое исключений не записываются в журнал приложения |

## Подписка и устаревание

Миграция SQLite **9 → 10** добавляет `notification_outbox.target_snapshot` и индекс поиска новых серий чата. Целевая группа записывается при постановке основного уведомления. Для старых строк снимок остаётся `NULL`: исходная группа не восстанавливается из текущего профиля, поэтому комментарии к таким строкам пропускаются.

Комментарий не отправляется, если группа изменилась, уведомления выключены, бот удалён из чата, серия не доставлена полностью или для этого чата уже существует более новое уведомление. Неактуальная генерация отменяется. При завершении приложения единственный worker отменяется с ожиданием очистки CLI.

Изменение группы, выключение уведомлений и обработчик удаления бота используют ту же блокировку назначения, что и финальная отправка комментария. Если Telegram-запрос уже начался, изменение настроек завершается после его окончания; подтверждение отключения не обгоняет такую отправку. Приложение не добавляет повтор комментария при неопределённом сетевом результате. Ограничения общей Telegram-сессии рассматриваются отдельно в AUD-02; строгая однократная доставка не обещается.

Задание содержит только ID импорта и срок действия, без `ParsedSchedule` и списков изменений. Память недавно обработанных ID ограничена 128 записями. Повтор того же импорта в этой истории не добавляет новое задание. Перезапуск не восстанавливает историю комментариев и не запускает их повтор из основной очереди.

## Данные и CLI

Функцию включает оператор через серверный `.env` и список разрешённых чатов. Администратор группы может остановить комментарии, выключив уведомления чата. Grok получает подготовленный текст опубликованного расписания этого чата. Private-уведомления, список подписчиков, название Telegram-чата, токен бота и ключ аналитики в запрос не включаются.

Дочерний процесс получает ограниченный набор переменных ОС, proxy/certificate settings и собственную авторизацию Grok (`HOME`, `XAI_API_KEY`, `GROK_*`). Переменные Telegram, аналитики и базы ему не передаются. Рабочий каталог — отдельный временный каталог. Существующие ограничения tools, web search и subagents сохранены, ответ отправляется как простой текст с `parse_mode=None`.

Готовая реплика живёт в памяти текущего задания и не сохраняется приложением в SQLite или его логи. Каталог `~/.grok` принадлежит самому CLI и может содержать его сессии наряду с авторизацией; это отдельное хранилище, его нельзя публиковать или включать в release archive. Фильтрация окружения не создаёт отдельную файловую песочницу: CLI выполняется под пользователем `bot`.

## Сборки

```sh
# Бот без скачивания CLI; реакции должны быть выключены.
docker build --target core -t schedule-bot:core .

# Стандартный образ для текущего сервера с Grok.
docker build --target with-grok -t schedule-bot:with-grok .
```

Versioned release tools по-прежнему собирают стандартный `with-grok` и проверяют его CLI до остановки работающего бота. Core-вариант предназначен для установки без функции Grok; его offline smoke входит в CI.

## Регрессии

`tests/test_grok_security.py` проверяет отключение и смену группы до/во время генерации, удаление бота, новый импорт, ожидание всей серии при backoff, отказ основной доставки, выборку из 25 тысяч private-доставок, очередь на 100 событий, дедупликацию, TTL, отсутствие повторов после рестарта, миграцию и её откат, переполнение обоих потоков CLI, фильтрацию секретов и безопасные логи, последовательные subprocess и очистку при отмене. Проверки используют fake CLI и имитацию Telegram.
