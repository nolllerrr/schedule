# Обслуживание и ошибки

Команды ниже выполняются в окружении установленного проекта. Для Docker добавьте `docker compose exec bot` перед `schedule-bot`, например: `docker compose exec bot schedule-bot backup`.

## Команды обслуживания

| Команда | Что проверяет или меняет |
| --- | --- |
| `/update` в личном чате | Проверяет сайт, импортирует изменения, будит доставку и синхронизирует закрепления; только для администратора бота |
| `/stats`, `/stats 30` | Статистика за 7 дней или указанный период; период ограничивается 1–90 днями; только для администратора бота |
| `schedule-bot doctor` | Находит ссылку на расписание на странице и вызывает Telegram `getMe`; требует токен |
| `schedule-bot update` | Получает актуальный файл и импортирует его в базу |
| `schedule-bot parse FILE` | Разбирает локальную книгу и печатает число занятий, групп, диапазон и предупреждения |
| `schedule-bot parse FILE --json` | Печатает JSON нормализованных занятий |
| `schedule-bot import-file FILE` | Проверяет и импортирует локальный файл |
| `schedule-bot import-file FILE --approval-reason "Причина проверки"` | Разрешает проверенные аномалии охвата или количества занятий; структурные ошибки остаются заблокированными |
| `schedule-bot retry-notifications IMPORT_ID DESTINATION_ID --kind user` | Возвращает недоставленные части личной серии в очередь |
| `schedule-bot retry-notifications IMPORT_ID CHAT_ID --kind chat` | То же для группового чата |
| `schedule-bot backup` | Создаёт согласованную копию SQLite с проверкой целостности |

`doctor` не скачивает и не разбирает Excel, не импортирует расписание и не проверяет доставку конкретному пользователю. Успех этой команды подтверждает только проверенные соединения.

`parse` не изменяет базу. Некоторые ошибки структуры возвращаются внутри `ParsedSchedule.validation_errors`, а CLI `parse` их не выводит; поэтому успешный разбор не означает, что импорт будет разрешён. Полная проверка перед активацией выполняется `import-file` или `update`.

CLI `update` и `import-file` сохраняют задания доставки, но сами их не рассылают: очередь обработает работающий бот. Они не обслуживают мониторинг инцидентов источника. Ручная Telegram-команда `/update` использует работающий `ScheduleOutageTracker` и может подтвердить восстановление.

В штатном режиме пользуйтесь `/update`: она разделяет блокировку с автоматической проверкой. Отдельный процесс CLI этой блокировки не разделяет, хотя транзакции SQLite защищают запись данных. Не запускайте второй polling-процесс с той же базой.

## Если сайт расписания недоступен

Загрузчик повторяет временные сетевые ошибки и HTTP 408, 429, 500, 502, 503, 504. Остальные HTTP-ошибки, например 403 или 404, не повторяются. Попытки и максимальные паузы настраиваются в [конфигурации](configuration.md#источник-и-расписание).

Обычные паузы растут примерно как 2, 4, 8 секунд со случайным разбросом ±20%. Для 429 и 503 корректный `Retry-After` заменяет эту паузу, сохраняя настроенный верхний предел. На каждую попытку установлен общий дедлайн 30 секунд, включая редиректы и чтение ответа. Страница и файл — отдельные запросы. При стандартных настройках верхняя оценка одного запроса составляет 165 секунд, двух последовательных запросов — 330 секунд, без учёта последующего разбора и импорта.

Мониторинг считает не внутренние HTTP-попытки, а завершившиеся неудачей автоматические проверки:

| Состояние | Что происходит |
| --- | --- |
| `HEALTHY` | Источник доступен; счётчик последовательных сбоев обнулён |
| `DEGRADED` | Уже есть неудачные проверки, но порог предупреждения ещё не достигнут |
| `DOWN` | Порог достигнут; каждому настроенному администратору поставлено одно предупреждение об инциденте |

Повторные временные ошибки до успеха относятся к одному инциденту. После реального успешного получения страницы и файла, в том числе подтверждения кеша через HTTP 304, источник возвращается в `HEALTHY`. Восстановление отправляется только тем администраторам, которым предупреждение было подтверждённо доставлено; ещё ожидающие предупреждения отменяются.

Неудачная `/update` не увеличивает счётчик автоматических проверок. Ошибки структуры страницы, формата файла, парсинга, импорта и SQLite не скрываются этим счётчиком: это отдельные ошибки. Восстановление доступа к сайту также не означает, что последующий импорт обязательно прошёл.

При неудачной загрузке уже принятое расписание остаётся доступным. Состояние инцидента и административная очередь переживают перезапуск. Постоянный отказ Telegram завершает административную доставку, временный — переносит следующую попытку. Если SQLite недоступна для записи, критическое оповещение пробуется напрямую, а диагностика остаётся в журнале.

## Доставка уведомлений

Адресаты и текст фиксируются вместе с импортом. Одна серия определяется импортом, адресатом и его типом (`user` или `chat`). Части серии идут по порядку; следующая не отправляется, пока предыдущая не подтверждена.

- Доставленная часть остаётся `sent`; обычный повтор не отправляет её заново.
- Временный сбой сохраняет `pending` и срок следующей попытки: обычная задержка растёт от примерно 15 секунд до часа с разбросом ±20% и пределом в час. Число попыток не ограничено пятью.
- Ограничение Telegram `retry_after` учитывается отдельно.
- Постоянные `Forbidden` и `BadRequest` завершают часть как `failed`, последующие части блокируются. Для недоступного группового чата также выключается активность профиля чата.
- Недоставленная пользовательская серия через семь дней завершается как устаревшая. Административная очередь использует отдельные правила и этого срока не имеет.
- Перед отправкой снова проверяются существование записи и действующая подписка. Удалённый профиль или отключённая подписка прекращают ожидающую доставку.

Worker обрабатывает обе очереди, ограничивает проход числом записей и выдерживает паузы отправки. После перезапуска он продолжает сохранённые задания без необходимости нового импорта. Нижележащие сетевые повторы Telegram настраиваются отдельно от этой очереди.

После устранения причины можно вернуть недоставленную серию в работу:

```sh
schedule-bot retry-notifications 42 123456789 --kind user
schedule-bot retry-notifications 42 -1001234567890 --kind chat
```

Числа здесь условные. `IMPORT_ID` — `imports.id`, ID адресата — поле `destination_id` очереди; это не порядковый ID записи доставки. Команда требует действующей подписки, сохраняет успешные части и заново задаёт семидневный срок недоставленным. Отправляется сохранённый текст выбранного импорта, который может отличаться от текущего расписания.

Повторный импорт того же SHA не создаёт новую рассылку. Команда повтора работает с существующей серией; отсутствующие исторические задания она не восстанавливает. Смена группы или личного профиля не переписывает старые задания: перед отправкой проверяется действующая подписка, но не совпадение её новой цели с прежним текстом. Поэтому ранее подготовленная серия может прийти и после смены группы.

Доставка рассчитана на один процесс. При аварийном завершении между принятием сообщения Telegram и записью подтверждения в SQLite возможен дубль: транзакция базы не может охватить внешний запрос Telegram.

## Карантин импорта

При `ImportQuarantinedError` рабочее расписание и очередь новой публикации не заменяются. Причины и разобранный снимок сохраняются в `quarantined_imports`.

1. Найдите причину в журнале и проверьте сам Excel.
2. При ошибке структуры дождитесь исправленного файла либо измените парсер и проверьте его тестами.
3. Если подтверждены законная отмена занятий или изменение охвата, импортируйте исходный файл с непустой причиной:

```sh
schedule-bot import-file "22.09.2026.xlsx" --approval-reason "Проверена отмена занятий в исходной публикации"
```

Причина остаётся в записи импорта. Флаг не разрешает ошибки структуры. Отдельной Telegram-команды подтверждения карантина нет. Подробные условия проверки и маркер пустого дня описаны в [формате Excel](excel.md#проверка-перед-активацией).

## Копии и восстановление

Бот создаёт обычную копию ежедневно в 03:30 по `TIMEZONE`. Перед миграцией существующей базы создаётся отдельная копия прежней схемы. Имена обычных файлов начинаются с `schedule-`, предмиграционных — с `pre-migration-`.

Ручная копия:

```sh
docker compose exec bot schedule-bot backup
```

Используется SQLite backup API, затем `PRAGMA quick_check` и атомарная публикация файла. Эта операция подходит для работающей базы; обычное копирование одного `.db` во время работы может не включить данные из WAL.

`BACKUP_RETENTION_COUNT` ограничивает только обычные копии. Предмиграционные копии не удаляются этой ротацией. Копия рядом с рабочими данными не защищает от потери всего сервера — нужные файлы сохраняйте также вне него.

Для восстановления остановите бот, сохраните текущий каталог данных отдельно, выберите совместимые версию программы и копию базы. Замените базу при остановленных процессах; относящиеся к прежней базе `-wal` и `-shm` сохраните отдельно и не переносите к восстановленному `.db`. Проверьте права записи, затем запустите один экземпляр. Изменения после времени копии при таком восстановлении не сохранятся.

## Журналы и рост данных

`run` пишет одновременно в консоль и файловый журнал рядом с базой. CLI-команды имеют консольный журнал. Для Docker доступны:

```sh
docker compose logs --tail=100 bot
docker compose exec bot tail -n 100 /app/data/logs/bot.log
docker stats --no-stream
```

Путь второй команды соответствует стандартному `DATABASE_PATH`. Файловый журнал ротируется по UTC; параметры хранения — в [конфигурации](configuration.md#хранение-копии-и-статистика). Docker отдельно хранит до трёх файлов по 10 МБ согласно `compose.yaml`.

Форматтер скрывает токены Telegram, учётные данные URL, query и fragment, сохраняя типы исключений и traceback. Сам журнал всё равно может содержать рабочие ID и другую техническую информацию; это не обезличенная статистика.

Подробные события статистики очищаются ежедневно в 04:00 по `TIMEZONE`. Для импортов, истории занятий, завершённых очередей, карантина, инцидентов и файлов Excel автоматическая очистка не реализована. Наблюдайте за размером `data/`; уменьшение срока статистики не очищает остальные данные.

Ограничения XLSX, числа обработчиков и временных диалогов уменьшают отдельные расходы, но не задают общий предел RAM. При высоком потреблении памяти сравнивайте состояние процесса до и после импорта и смотрите метрики контейнера; точные бюджеты чтения перечислены в [описании Excel](excel.md#бюджет-чтения).

## Обновление и откат

1. Получите новую версию исходников и выполните [тесты](architecture.md#проверка-изменений).
2. До переключения создайте проверенную копию базы и сохраните её вне рабочего каталога данных. Сохраните прежний образ или возможность его воспроизвести.
3. Соберите новый образ: `docker compose build bot`.
4. Остановите прежний контейнер: `docker compose stop bot`. Запустите новый: `docker compose up -d --no-deps bot`. Сохраните `.env` и существующий `./data`.
5. Проверьте журнал запуска, просмотр расписания, `/update`, доставку и закрепления. Если требовалась миграция, проверьте наличие предмиграционной копии.

Для отката после несовместимой миграции остановите новую программу и восстановите совместимую копию вместе с прежним образом. Более старая программа может отказаться открывать новую схему — одного возврата образа недостаточно.
