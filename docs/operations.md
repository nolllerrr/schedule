# Обслуживание и ошибки

Команды выполняются в окружении установленного проекта. Для обычного Compose добавьте `docker compose exec bot` перед `schedule-bot`. После развёртывания через release tools используйте Compose-путь текущего release из `.current-release.json`.

## Команды обслуживания

| Команда | Что проверяет или меняет |
| --- | --- |
| `/update` в личном чате | Проверяет публикации, импортирует изменения, будит доставку и синхронизирует закрепления; только для администратора бота |
| `/stats`, `/stats 30` | Статистика за 7 дней или указанный период 1–90 дней; только для администратора |
| `schedule-bot health --json` | Читает локальный heartbeat готовности; не открывает базу и не требует токена или внешней сети |
| `schedule-bot doctor` | Находит ссылку на странице источника и вызывает Telegram `getMe`; требует токен |
| `schedule-bot update` | Проверяет все выбранные публикации и атомарно активирует итоговое расписание с outbox |
| `schedule-bot update --approval-reason "Причина"` | Разрешает проверенные аномалии собранного расписания; не обходит структурные ошибки и конфликт равных приоритетов |
| `schedule-bot parse FILE [--json]` | Разбирает локальную книгу; с `--json` печатает нормализованные занятия |
| `schedule-bot import-file FILE [--approval-reason "Причина"]` | Проверяет и импортирует отдельный локальный файл |
| `schedule-bot retry-notifications IMPORT_ID DESTINATION_ID --kind user` | Возвращает недоставленные части личной серии в очередь |
| `schedule-bot retry-notifications IMPORT_ID CHAT_ID --kind chat` | То же для группового чата |
| `schedule-bot delivery-attempts --limit 100` | Показывает ещё не проверенные попытки с исходом `uncertain` / `accepted` |
| `schedule-bot review-delivery-attempt ID --reason "Причина"` | Отмечает попытку проверенной оператором; не меняет исход и не повторяет отправку |
| `schedule-bot cleanup [--limit 100]` | Показывает кандидатов на очистку без удаления |
| `schedule-bot cleanup --apply [--limit 100]` | Удаляет допустимый ограниченный пакет технических записей и файлов |
| `schedule-bot backup` | Создаёт согласованную копию SQLite с проверкой целостности |

`health` проверяет свежесть heartbeat polling, worker и планировщика. Его успех не подтверждает доступность сайта или актуальность расписания. `doctor` проверяет соединения, но не разбирает XLSX и не подтверждает доставку конкретному пользователю.

`parse` не изменяет базу. Некоторые ошибки структуры возвращаются в `ParsedSchedule.validation_errors`, а CLI `parse` их не выводит; успешный разбор не означает разрешение на активацию. Полную проверку выполняют `import-file` и `update`.

CLI `update` и `import-file` сохраняют очередь, но сами её не рассылают. CLI не обслуживает инциденты источника; Telegram-команда `/update` использует работающий tracker и может подтвердить восстановление. В штатном режиме пользуйтесь `/update`: она разделяет блокировку с автоматической проверкой. Отдельный CLI-процесс этой блокировки не разделяет. Поддерживается один polling-процесс на базу.

## Актуальность сохранённого расписания

Время успешной проверки относится к получению и принятию всего набора публикаций, включая проверку неизменных сохранённых снимков. Успешная HTTP-загрузка сама по себе его не обновляет, если разбор или импорт завершились ошибкой.

До первой успешной проверки показывается неподтверждённая актуальность. После ошибки или превышения `SCHEDULE_STALE_AFTER_MINUTES` — предупреждение о возможной устарелости с прежним временем успеха. При недоступном источнике сохранённые занятия остаются доступны. Закрепления обновляют предупреждение при смене состояния, а не в каждом цикле.

Неудачная `/update` показывает безопасный код, этап и причину: например HTTP-код, timeout, разбор Excel, карантин или база данных. Полный traceback остаётся в журнале; текст исключения и секретные URL в Telegram не отправляются.

## Если сайт расписания недоступен

Загрузчик повторяет временные сетевые ошибки и HTTP 408, 429, 500, 502, 503, 504. Остальные HTTP-ошибки, например 403 или 404, не повторяются. Попытки и максимальные паузы задаются в [конфигурации](configuration.md#источник-и-расписание).

Обычные паузы растут примерно как 2, 4, 8 секунд с разбросом ±20%. Для 429 и 503 корректный `Retry-After` заменяет паузу, сохраняя настроенный предел. Одна попытка ограничена 30 секундами, вся сетевая часть проверки — 300 секундами. Разбор каждого нового файла стандартным сетевым парсером выполняется отдельно, с дедлайном 60 секунд.

Мониторинг считает завершившиеся неудачей автоматические проверки, а не внутренние HTTP-попытки:

| Состояние | Что происходит |
| --- | --- |
| `HEALTHY` | Нет незакрытого инцидента временной недоступности |
| `DEGRADED` | Неудачные проверки есть, порог предупреждения ещё не достигнут |
| `DOWN` | Порог достигнут; администраторам поставлено одно предупреждение об инциденте |

Разные временные сетевые ошибки до успеха относятся к одному инциденту. Периодических напоминаний о нём нет. После реального успешного получения всех выбранных файлов, в том числе HTTP 304, tracker возвращается в `HEALTHY`. Восстановление отправляется только получателям подтверждённо доставленного предупреждения; ещё ожидающие предупреждения отменяются.

Ручная неудачная `/update` не увеличивает счётчик автоматических проверок. Ошибки структуры страницы, XLSX, парсинга, импорта и SQLite сообщаются отдельно. Одинаковый безопасный текст критической ошибки для одного администратора объединяется, пока прежняя доставка ожидает, либо в течение шести часов; другая причина ставится сразу. Это отдельное ограничение повторов, а не новый инцидент источника. Восстановление сети не означает успешного принятия расписания.

Инцидент и административная очередь переживают перезапуск. Постоянный отказ Telegram завершает доставку, временный переносит следующую попытку. Если SQLite недоступна для записи, критическое сообщение пробуется напрямую, а диагностика остаётся в журнале.

## Доставка уведомлений

Адресаты и неизменяемый текст сохраняются вместе с effective import. Серия определяется импортом, адресатом и его типом (`user` / `chat`). Следующая часть не отправляется до подтверждения предыдущей.

- Доставленная часть остаётся `sent`; обычный повтор её не отправляет заново.
- Временный сбой сохраняет `pending` и время следующей попытки; задержка растёт примерно от 15 секунд до часа с разбросом ±20%. Пяти попытками доставка не ограничена.
- `retry_after` Telegram учитывается отдельно.
- Постоянные `Forbidden` / `BadRequest` завершают часть как `failed` и блокируют продолжение; недоступный групповой чат также деактивируется.
- Пользовательская недоставленная серия через семь дней завершается как устаревшая. У административной очереди отдельные правила без этого срока.
- Перед отправкой повторно проверяются запись и действующая подписка. Удаление профиля или отключение подписки прекращает ожидающую доставку.

Worker обрабатывает обе очереди ограниченными проходами и продолжает задания после перезапуска. Длинные HTML-сообщения разделяются с сохранением видимого текста и самостоятельной валидности частей; лимит учитывает UTF-16 после разбора сущностей.

После устранения причины можно вернуть недоставленную серию в работу:

```sh
schedule-bot retry-notifications 42 123456789 --kind user
schedule-bot retry-notifications 42 -1001234567890 --kind chat
```

Числа условные. `IMPORT_ID` — ID effective import, ID адресата — `destination_id`, а не ID строки доставки. Команда требует подписки, сохраняет успешные части и заново задаёт семидневный срок. Отправляется сохранённый текст выбранной серии, который может отличаться от текущего расписания. Исторические отсутствующие задания не восстанавливаются.

Повтор неизменной проверки не создаёт новую рассылку. Смена профиля не переписывает старые задания: проверяется действующая подписка, но не совпадение новой цели с прежним текстом. Поэтому подготовленная серия может прийти после смены группы.

### Неопределённый результат отправки

Telegram и SQLite не образуют общую транзакцию. Потеря ответа или сбой между принятием сообщения Telegram и записью `sent` могут привести к повтору; строго однократная отправка не гарантируется, включая сетевые повторы Telegram-сессии.

`delivery_attempts` сохраняет начало попытки, исход (`uncertain`, `accepted`, `rejected`, `sent`), известный Telegram message ID и безопасную категорию ошибки. Сопоставляйте ID попытки с журналом и самой серией:

```sh
schedule-bot delivery-attempts --limit 100
schedule-bot review-delivery-attempt 17 --reason "Проверены журнал и состояние доставки"
```

Отметка проверки — только запись диагноза оператора. Она не делает сообщение доставленным, не меняет очередь и не вызывает повтор. После проверки для недоставленной серии применяется отдельная команда `retry-notifications`. Непроверенные `uncertain` / `accepted` защищены от обычной очистки.

## Миграция Telegram-группы в супергруппу

Служебные сообщения `migrate_to_chat_id` / `migrate_from_chat_id` и ошибка
`TelegramMigrateToChat` при отправке уведомления автоматически переносят профиль
группы и очередь на новый ID в одной транзакции. После отклонённой отправки бот
сразу повторяет её на новый ID; отклонение сохраняется в журнале попыток как
`rejected`, а не `uncertain`. В лог выводится `Telegram group migration applied`
без идентификаторов чата.

Учебная группа, согласие на уведомления и настройка закрепления сохраняются.
Старые ID закреплённых сообщений сбрасываются: очередная синхронизация проверит
права и опубликует закрепление заново. Если новый чат уже настроен, его настройки
имеют приоритет; ожидающие сообщения для другой учебной группы отменяются.
Совпадающие части очереди объединяются с сохранением истории попыток и статуса
подтверждённой отправки. Истёкшие и окончательно неудачные доставки автоматически
не возобновляются. Изменение схемы SQLite для этого исправления не требуется.

## Карантин импорта

При `ImportQuarantinedError` активное расписание и новая очередь не заменяются. Причины и разобранный снимок сохраняются в `quarantined_imports`. Снимки отдельных источников могут уже храниться в базе, пока их активация отклонена.

1. Найдите причину в журнале и проверьте исходные книги.
2. При структурной ошибке исправьте файл или парсер; конфликт публикаций одинакового приоритета требует однозначного источника.
3. Для законной аномалии охвата или количества используйте непустую причину:

```sh
schedule-bot update --approval-reason "Проверена отмена занятий в исходных публикациях"
schedule-bot import-file "22.09.2026.xlsx" --approval-reason "Проверена отмена в этом файле"
```

Для повторной активации известного снимка в составе публикаций используйте `update --approval-reason`; обычный локальный импорт известного SHA может вернуть `skipped`. Причина сохраняется в effective import. Структурные ошибки и конфликт равных приоритетов флагом не обходятся. Telegram-команды подтверждения нет. Условия и маркер пустого дня описаны в [формате Excel](excel.md#проверка-перед-активацией).

## Копии и восстановление

Обычная проверенная копия создаётся ежедневно в 03:30 по `TIMEZONE`; перед миграцией — отдельная копия прежней схемы. Ручной запуск: `schedule-bot backup`. SQLite backup API учитывает WAL, затем проверяется целостность и файл публикуется атомарно. Обычное копирование одного работающего `.db` не даёт такой гарантии.

`BACKUP_RETENTION_COUNT` ограничивает обычные `schedule-*.db`; предмиграционные копии сохраняются отдельно. Вместе с базой сохраняйте `<DATABASE_PATH>.analytics-salt` либо явно заданные текущий и прежние секреты. SQLite backup сам их не включает. При восстановлении без прежнего ключа удаление старой статистики по пользователю может стать невозможным.

Для offline-проверки и восстановления в новый, несуществующий путь предусмотрены:

```sh
python scripts/backup_tools.py verify path/to/backup.db
python scripts/backup_tools.py restore path/to/backup.db isolated/restored.db
```

Команды проверяют целостность и внешние ключи; отчёт содержит схему, счётчики и хеши без содержимого строк. Публичная команда restore не заменяет рабочую базу. Локальная копия не защищает от потери сервера; настройка внешнего хранилища в эту реализацию не входила.

Для рабочего восстановления остановите единственный бот, сохраните прежние данные отдельно и выберите совместимые программу, базу и ключ аналитики. WAL/SHM от прежней базы не переносите к восстановленному `.db`. Восстановление снимка теряет более поздние изменения и может повторить внешние сообщения, подтверждённые после его создания.

## Журналы и рост данных

`run` пишет консольный и файловый журнал рядом с базой. Стандартные пути Docker:

```sh
docker compose logs --tail=100 bot
docker compose exec bot tail -n 100 /app/data/logs/bot.log
docker stats --no-stream
```

Файловый журнал ротируется по UTC; Docker хранит до трёх файлов по 10 МБ. Форматтер скрывает Telegram-токены, URL credentials, query и fragment, сохраняя типы исключений и traceback. Рабочие ID в журнале возможны: это не обезличенная статистика.

Подробная статистика очищается в 04:00, технические данные — в 04:30 по `TIMEZONE`. Сроки задают `ANALYTICS_RETENTION_DAYS`, `OUTBOX_RETENTION_DAYS`, `DOWNLOADS_RETENTION_DAYS`. Сначала можно оценить отдельный пакет:

```sh
schedule-bot cleanup --limit 100
schedule-bot cleanup --apply --limit 100
```

Очищаются старые целиком завершённые серии и связанные попытки, а также незащищённые hash-prefixed XLSX. Не удаляются серии с `pending`, непроверенная неопределённость, незакрытые административные инциденты, используемые source snapshots / активные файлы, файлы ожидающего карантина, `.part`, ссылки и нераспознанные имена. Лимит ограничивает число серий обеих очередей вместе и отдельно число файлов. История импортов, занятий, карантина и инцидентов сохраняется; очистка не задаёт общий предел базы или RAM.

## Обновление и откат

Runtime/build зависимости закреплены хешами, базовый Python-образ — digest. [CI workflow](../.github/workflows/checks.yml) описывает проверки и сборку; статус CI и защита ветки проверяются отдельно для нужного коммита.

Для развёртывания используется пакет выбранного коммита, новый release-каталог, проверка манифеста, резервирование прежнего образа и базы, offline-репетиция миграции и проверка runtime heartbeat. Не изменяйте `.env`, ключ аналитики и постоянный `data/` при замене кода. Поддерживаются автоматический откат неудачного переключения и явный откат:

```powershell
./deploy.ps1 -Plan
./deploy.ps1 -RollbackRelease '<SHA>-<UTC timestamp>'
```

После несовместимой миграции откат требует прежнего образа и совместимого снимка базы. При той же схеме ручной откат по умолчанию сохраняет текущие данные; `-RestoreDatabase` явно восстанавливает и снимок. Подробные условия, пути release, блокировки и сохранение неудачной базы описаны в [операционном руководстве](../scripts/OPERATIONS.md). Наличие этих инструментов в репозитории не означает выполненный деплой или проверку рабочего сервера.
