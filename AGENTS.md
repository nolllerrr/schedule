# Repository Guidelines

Инструкции для агентов, работающих с этим репозиторием. Применяются ко всему дереву проекта; дополнительные `AGENTS.md` в подкаталогах уточняют правила для своего участка. Явные указания пользователя определяют объём задачи. Выполняйте работу до проверенного результата, сохраняя изменения пользователя.

## Назначение проекта

Это Telegram-бот расписания Петрозаводского архитектурно-строительного техникума. Он загружает Excel для корпуса 1, сохраняет версии расписания в SQLite, показывает занятия студентам и преподавателям, уведомляет групповые чаты, обновляет закрепления и принимает обращения об ошибках. Grok-комментарии — дополнительная функция.

Стек: Python 3.14+, aiogram 3, APScheduler, SQLite, openpyxl и Pillow. Точную версию Python берите из `.python-version`, зависимости — из `pyproject.toml` и lock-файлов. Приложение использует long polling; отдельного HTTP-сервера нет.

## Порядок работы агента

1. Выполните `git status --short`, определите текущую ветку и прочитайте инструкции для изменяемых каталогов. Не отменяйте чужие правки и не очищайте рабочее дерево ради удобства.
2. Найдите затронутый сценарий через `rg`, прочитайте реализацию, ближайшие тесты и профильный документ из таблицы ниже. Перед исправлением установите причину ошибки.
3. Вносите изменения в модуль, отвечающий за поведение. Сохраняйте существующие интерфейсы, если задача не требует их изменения; избегайте попутного форматирования и несвязанных рефакторингов.
4. Для исправления поведения добавьте регрессионный тест; для новой функции проверьте успешный сценарий, ошибки и затронутые права доступа. Для правок только документации новые тесты не нужны.
5. Запустите подходящие проверки, просмотрите итоговый diff и обновите документацию изменённого поведения. Недоступную проверку явно укажите в отчёте.
6. В финальном ответе кратко сообщите, что изменено, что проверено и какие ограничения остались. Различайте локальные проверки и результат удалённого CI; не объявляйте деплой выполненным по одной успешной сборке.

При расхождении документации с реализацией сверяйте код и тесты; исправляйте связанный с задачей устаревший текст. Номера схем, версии шаблонов и числовые лимиты проверяйте в исходниках, а не переносите из старого описания.

## Окружение и установка

Запускайте команды из корня нужного checkout. В Windows используйте явный путь к Python окружения. Editable-установка может указывать на другой worktree; проверяйте привязку исходников через `scripts/run-local.ps1 -Check`.

```powershell
py -3.14 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --require-hashes -r build-requirements.lock -r dev-requirements.lock
.\.venv\Scripts\python.exe -m pip install --no-deps --no-build-isolation -e .
.\.venv\Scripts\python.exe -m pip check
```

В Linux создайте окружение через `python3.14 -m venv .venv` и используйте `.venv/bin/python` с теми же аргументами. Активация окружения необязательна.

Для работы бота скопируйте `.env.example` в `.env` и настройте `BOT_TOKEN`. Обычным тестам реальный токен не нужен. Не перезаписывайте существующий `.env` пользователя. Относительные пути данных зависят от рабочего каталога.

## Команды разработки и проверки

Ниже `python` и `uv` означают инструменты установленного окружения; в Windows используйте `.\.venv\Scripts\python.exe` и `.\.venv\Scripts\uv.exe`.

```sh
python -m ruff check --select F src tests scripts
python -m pytest tests/test_parser.py
python -m pytest --basetemp=.pytest-tmp-run
python scripts/update_locks.py --check
uv build --wheel --out-dir .pytest-tmp-wheel
docker build --target core -t schedule-bot:core-check .
docker build -t schedule-bot:check .
```

- Ruff проверяет ошибки категории `F`; отдельный formatter в проекте не настроен. Не запускайте массовое автоформатирование.
- Сначала запускайте затронутые тесты, затем полный pytest для изменений кода. `--basetemp` должен указывать на отдельный временный каталог: pytest может удалить его содержимое.
- При изменении зависимостей проверяйте `pip check` и актуальность экспортов; при изменении упаковки, assets, Docker или установщика проверяйте wheel/образы и соответствующие offline smoke checks из `.github/workflows/checks.yml`.
- CI выполняет установку по хешам, проверку lock-экспортов, Ruff, pytest, сборку `core` и полного образа, затем проверки без сети. Полный образ включает Grok CLI; `core` собирается без него.
- Не меняйте тесты или настройки CI только ради сокрытия ошибки. Сбой окружения и дефект приложения описывайте отдельно.

### Локальный запуск и диагностика

```powershell
.\scripts\run-local.ps1 -Check
.\scripts\run-local.ps1
```

`-Check` показывает путь загруженного репозитория и версию схемы без polling. Обычный запуск выставляет `PYTHONPATH` на `src/` текущего checkout и выполняет бота. Альтернатива после установки — `python -m schedule_bot run`.

- `python -m schedule_bot parse path/to/05.10.2026.xlsx --json` разбирает локальную книгу без импорта в БД. Имя должно содержать поддерживаемую дату или диапазон.
- `python -m schedule_bot health --json` читает локальный heartbeat; без работающего экземпляра ожидается состояние `not ready`.
- `python -m schedule_bot doctor` обращается к сайту и Telegram API.
- `import-file`, `update`, `retry-notifications`, `backup` и `cleanup --apply` затрагивают данные или очереди. Проверяйте их только на предназначенном для задачи экземпляре или изолированной копии.
- Некоторые команды просмотра БД тоже вызывают её подготовку и миграции. Перед запуском изучите ветку команды в `cli.py`; отсутствие отправки сообщений не означает отсутствие записей на диск.

## Стиль кода и границы модулей

Используйте отступы в четыре пробела, type annotations, `snake_case` для функций и модулей, `PascalCase` для классов, `UPPER_SNAKE_CASE` для констант. Следуйте стилю соседнего кода. Пользовательские тексты и документация проекта преимущественно русскоязычные; сохраняйте терминологию интерфейса.

- Размещайте бизнес-правила в domain/service/repository-слое; обработчикам Telegram оставляйте проверку контекста и вызов нужной операции.
- Сохраняйте возможность использовать парсер, репозиторий и CLI импорта без импорта aiogram. Не добавляйте сетевые вызовы и запуск задач при импорте модуля.
- Новые настройки проводите через `Settings`, проверку значений, `.env.example`, `docs/configuration.md` и тесты конфигурации. Секреты и пути окружения не зашивайте в код.
- Для дат используйте принятую в приложении настройку `TIMEZONE`, а в тестах — заданное время или существующий механизм clock. Не привязывайте бизнес-логику к часовому поясу машины.
- Новая зависимость должна решать задачу, которую не покрывают стандартная библиотека и текущий стек. Меняйте её декларацию и lock-файлы согласованно.

## Инварианты импорта и модели расписания

- Выбор публикации выполняется отдельно для даты; более узкий диапазон имеет приоритет. Различающиеся публикации одинакового приоритета дают конфликт. Не заменяйте этот алгоритм выбором последней ссылки или HTTP-даты.
- Ошибочный или неподтверждённый импорт не должен заменять принятое расписание и создавать уведомления о его удалении. Сохраняйте карантин, проверку охвата и проверку ранее сохранённых снимков при их повторной активации.
- Пустой день, отсутствие даты в источнике и ошибка разбора — разные состояния. Не выводите отмену занятий из отсутствующего или нераспознанного блока.
- `--approval-reason` допускает рассмотренные аномалии охвата/количества; он не обходит структурные ошибки и конфликты приоритетов.
- Идентичность снимка учитывает содержимое и диапазон исходного имени. Сохраняйте повторяемость импорта и отсутствие лишних уведомлений при неизменившихся данных.
- `Lesson.segments` хранит связи предмета, преподавателя, аудитории и подгруппы. Не сводите их к независимым спискам. Преподаватель должен видеть относящиеся к нему сегменты.
- Различайте `position` и `lesson_number`: классный час может не иметь номера пары. Нормализация отображения не должна уничтожать диагностические значения `raw_data`.
- Сохраняйте ограничения скачивания, ZIP/XML, памяти, числа ячеек и времени разбора. Стандартный разбор книги выполняется в завершаемом дочернем процессе; при отмене или таймауте освобождайте процесс и временные файлы.

## SQLite, миграции и async-код

- Поддерживается один работающий процесс бота на одну БД. Не запускайте второй polling-процесс с рабочим токеном для проверки изменения.
- Версию схемы определяет `ScheduleRepository.SCHEMA_VERSION`. Изменения схемы оформляйте очередной последовательной транзакционной миграцией; сохраняйте отказ от открытия более новой неподдерживаемой схемы.
- Проверяйте миграцию существующей базы и инициализацию пустой. При изменении схемы учитывайте backup перед миграцией и репетицию release на копии.
- Сохраняйте WAL, foreign keys, busy timeout и атомарность изменения расписания вместе с созданием записей очереди. Сетевые запросы внутри SQLite-транзакций недопустимы.
- В async-обработчиках используйте `AsyncScheduleRepository`. Его ожидание завершения транзакции при отмене защищает блокировки получателя и закрепления; не заменяйте его произвольным `to_thread` без этой гарантии.
- Закрывайте соединения, включая ошибку инициализации. Контекст `with connection` управляет транзакцией, но сам по себе не закрывает SQLite-соединение.
- Сохраняйте существующие блокировки обновления, получателя и закрепления. Проверяйте остановку фоновых задач и освобождение ресурсов при частичном старте, ошибках и отмене.

## Telegram, доставка и обращения

- Для персональных callback проверяйте владельца, реального отправителя, чат и привязанное сообщение согласно контексту операции. Сохраняйте публичные кнопки просмотра группового расписания. Административные операции должны повторно проверять права; не полагайтесь на наличие кнопки у пользователя.
- Пользовательские значения экранируйте для HTML. Для обращений и Grok сохраняйте простой текст с `parse_mode=None`. Разбивайте длинные сообщения существующими средствами с учётом UTF-16 и корректности тегов.
- Сохраняйте durable outbox, ограничения частоты, backoff и обработку миграции чата. Успех Telegram API и запись подтверждения в SQLite — отдельные этапы.
- `uncertain`, `accepted`, `rejected` и подтверждённая доставка имеют разный смысл. Не отмечайте неопределённую отправку успешной или безопасной для повтора без основания. Журнал попыток не обеспечивает exactly-once; сбой между API и commit допускает дубликаты.
- При изменении закреплений сохраняйте безопасную замену, обработку нехватки прав и восстановление после сбоя.
- Обращения имеют собственные снимки, черновики, события и очередь. Не меняйте через них расписание, профиль и обычную доставку. Сохраняйте атомарность подтверждения, уникальные ключи операций, ревизии черновиков и проверку доступа к токенам.

## Карточки и Grok

Рендереры карточек должны оставаться чистым преобразованием domain-данных в PNG: без SQLite, Telegram и сети. Сохраняйте текстовый fallback, лимиты кеша/параллельности, нумерацию слотов и отдельное представление классного часа. При изменении шрифтов проверяйте упаковку assets и лицензии.

Для визуальной проверки создавайте синтетические примеры в отдельном каталоге:

```sh
python scripts/preview_schedule_cards.py --output .pytest-tmp-card-preview
python scripts/preview_change_cards.py --output .pytest-tmp-change-preview
```

Просматривайте PNG: длинные поля, пропуски пар, плотный день, классный час и преподавательскую выдачу. Скрипт change-примеров отказывается перезаписывать существующие файлы; выбирайте новый каталог. Обновляйте `docs/examples/` только когда примеры действительно изменились.

Grok остаётся дополнительной best-effort функцией: ошибка CLI не блокирует основную доставку. Сохраняйте разрешённые чаты, проверку актуального согласия и состояния чата, порядок после основной рассылки, ограниченную очередь и защиту от устаревших комментариев. Не передавайте CLI токен Telegram, ключ аналитики или данные БД. Сохраняйте ограниченное окружение subprocess, таймауты, лимиты stdout/stderr и очистку при отмене. Тестируйте через fake CLI.

## Зависимости, безопасность и рабочие данные

`uv.lock` — источник экспортов runtime/dev. Для целевого обновления меняйте декларацию зависимости и lock; для намеренного общего обновления используйте `uv lock --upgrade`. Затем выполняйте `python scripts/update_locks.py` и `python scripts/update_locks.py --check`. Build-зависимости задаются также в `scripts/build-requirements.in`. Хеши экспортов вручную не редактируйте.

Grok CLI закреплён в `scripts/grok-cli.lock.json` по версии, размеру и платформенному SHA-256. Сохраняйте проверку установщиком; не заменяйте её запуском удалённого shell-установщика. При обновлении Docker сохраняйте проверку базового digest и запуск от непривилегированного пользователя.

Не коммитьте `.env`, `.deploy.json`, токены, SSH-ключи, Grok `auth.json`, analytics salts, БД и их WAL/SHM, реальные загрузки и журналы. Не выводите их содержимое в диагностике и итоговом отчёте. Для сокрытия секретов используйте существующие функции очистки логов и проверяйте их тестами. `.coverage` — генерируемый файл; не включайте его изменения в несвязанную задачу.

Новые операции очистки должны учитывать удерживаемые очередями/снимками данные, сроки хранения и ограниченный размер пакета. Резервную копию и восстановление проверяйте средствами проекта на отдельной базе; не копируйте только основной файл работающей WAL-базы.

## Git, PR и развёртывание

Если для задачи нужна новая ветка, используйте `codex/<краткая-тема>`. Сохраняйте текущую ветку, когда она уже предназначена для задачи. Не выполняйте destructive reset/clean, переписывание истории или force push ради упрощения работы.

Сообщения коммитов в истории — короткие английские формулировки в повелительном наклонении: `Normalize numeric room identifiers from Excel values`, `Fix bot lifecycle cleanup`. Делайте отдельные логичные коммиты, когда коммит входит в задачу. В PR указывайте проблему, новое поведение, связанные issues, выполненные проверки и ограничения; для карточек и интерфейса прикладывайте визуальные примеры.

Разработка и локальные проверки сами по себе не означают задачу на production. Когда развёртывание входит в запрос, используйте существующий release-механизм и `scripts/OPERATIONS.md`, учитывая уже полученные указания пользователя.

- `./deploy.ps1 -Plan` готовит локальный план; `-PackageDirectory <path>` создаёт локальный release-пакет. Команды deploy/rollback подключаются к настроенному серверу.
- Для release требуется чистый закоммиченный checkout; пакет привязан к точному коммиту, манифесту и образу. Не обходите проверки пропуском тестов ради успешного переключения.
- Сохраняйте проверенную SQLite-копию, offline-репетицию миграции, проверку heartbeat нового процесса и откат при неудаче. Grok credentials хранятся отдельно от backup БД.
- После versioned release используйте Compose-путь из `.current-release.json`; запуск старого корневого `docker compose up --build` может вернуть прежнее дерево исходников.
- Не удаляйте deployment lock без проверки состояния операции. Восстановление снимка может потерять новые записи и повторить уведомления; репетируйте его на изолированной базе с fake Telegram.
- В workflow production развёртывание запускается вручную; обычный push не равен деплою. Успешный CI проверяйте для нужного коммита.

## Проверка перед завершением

Просмотрите `git diff --stat`, `git diff`, `git diff --check` и `git status --short`; отдельно проверьте новые untracked-файлы, которые обычный diff не показывает. Убедитесь, что в изменениях только файлы задачи, нужные тесты и документация, без секретов и случайных артефактов. Для правок только документации проверьте пути, ссылки и точность команд; запуск всего приложения не требуется.
